1. Assess

  • Scan the v11 model here. The overview counts the processes that will not compile on TM1 12 — any process with a BLOCKER. The migration utility carries them over and reports each on an error line ("Issue(s) found during TI Process migration"); they fail on TM1 12 until fixed. Its "Objects processed with problems" list is a different one: processes whose data-source file was not found. After the restore, the Data files tab uploads those files to the TM1 12 Files area and points each process at its new path.
  • With a TM1 v12 database connected in Arc, run the v12 compile check: it dry-runs every v11 process against the real v12 compiler and saves nothing.
  • Inventory what lives outside TM1: scheduled tasks, TM1RunTI, TM1py scripts, TM1 Web websheets, Perspectives and Architect, TM1 Applications, ODBC sources. PAfE must be 2.0.77 or later; only the OData REST API remains.

2. Prepare v11

  • First, decide on TM1 Applications (}tp_*): it does not exist in TM1 v12. If it is retired, the TM1 Applications tab deletes every }tp_* object after a backup.
  • Then Bedrock: the Bedrock tab shows which Bedrock processes are in use. Delete the unused ones now: Bedrock 4 calls functions TM1 12 does not have, so each one would migrate only to fail to compile there. The upgrade of the ones in use to Bedrock 5 runs on the TM1 12 database.
  • Then apply the fixes to what is left (every Apply backs up first, dry-run compiles, writes, re-reads and compiles; it rolls back on failure). A fix changes v11 behaviour until cutover — each finding says how.
  • A finding you decide to leave can be skipped (the eye icon on its row): it leaves the list and the counts, and Apply leaves its statement as it is. Skips are remembered for this instance in this browser; Show skipped brings them back. Each object name opens the object in Arc.
  • Prepare CloudID (CloudID tab) before converting: the utility reads it. Once the element exists, only clients with a value migrate; their private views and subsets move with them.
  • Rename objects whose names contain \ / : * ? " < > | ' ; ,; fix element-type conflicts (N in one hierarchy, C in another — the utility stops at the first); delete or repair views on missing elements.
  • Move source files under the data directory: directories outside DatabaseDirectory are ignored, and TM1 12 confines TI files to the content area.
  • ODBC: install the ODBC Data Connector (ODBCIS) near the data — 64-bit system DSN, CA-signed certificate, port 5555, IP allow-list; set ODBCServiceRoot in PAW.
  • TI paths: use forward slashes (/), not backslashes — TM1 12 runs on Linux.
  • Groups: a }GroupProperties dimension and cube with a CloudID element choose and rename the groups that migrate (CloudID tab). Clients whose names are CAM IDs can take their e-mail address with the utility's --extract-cam-emails option.

3. Convert

  • This plugin prepares the model; IBM's Database Migration Utility converts it into a valid TM1 12 backup file to upload.
  • Download the utility from Planning Analytics on the cloud: Administration → Databases, the download icon at the top right, then Database Migration Utility. The same menu offers the ODBC Data Connector.
  • Free disk of 2.5× the database size, plus RAM to load it. Then, in order, in step 3 on the Overview of the v11 database: the tm1s.cfg line must not be red (the utility needs DatabaseDirectory); Save data runs SaveDataAll, because the utility reads the files on disk, not the server's memory; Copy the command and run it on the v11 host from the utility's bin64 folder; Read migrate.log to compare what it rejected with the scan.
  • Old feeder files: start the model on a recent v11 release before saving, so TM1 writes the feeder files in the latest format — the one the utility expects.
  • Stop the v11 service before converting (or at least use Save data), so every in-memory change is on disk and no file is in use while the utility reads the data directory.
  • The log is JSON lines; an error means that object is not in the output. Fix it on v11 (step 2) and convert again.

4. Create and restore

  • PAW → Administration → Databases → Create, with the same name as v11 (names are case-sensitive and cannot be renamed); RAM/CPU ≥ v11; Backup → Upload → Restore.

5. Verify v12

  • Scan the v12 database here. Open MDX subsets and views: a subset referenced by identifier ([dim].[hier].[subset]) returns an empty set with no error in TM1 12 — use TM1SubsetToSet.
  • Open the Bedrock tab on the TM1 12 database: it upgrades the Bedrock processes in use to Bedrock 5, installs the ones callers need, updates the callers, and deletes the unused ones.
  • Rebuild chores in PAW; upload external files to Contents('Files'); delete }Capabilities; move }CubeProperties settings to cube properties; validate data per cube; re-baseline performance.
